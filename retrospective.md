# Retrospective — FlyRank ML Internship

When I started the FlyRank ML Internship, my goal was to learn how machine learning could be applied to a real search-intelligence problem rather than only working with small practice datasets. I wanted to build something that could turn search-performance data into a useful recommendation for a real team. My project eventually became a content-refresh prioritization system that uses anonymized Google Search performance data to identify which pages should be reviewed first.

At the beginning, I was mainly focused on understanding the dataset, exploring its features, and building a readable machine-learning model. As the project developed, I realized that training a model was only one part of the problem. The more important question was what decision the model was supposed to support. Instead of asking, “Can I predict performance?” I reframed the problem as, “If a content team has limited time, which pages should they investigate first?” This changed the way I approached the entire pipeline.

I built a reproducible workflow that moves from data preparation and feature engineering to baseline scoring, model training, evaluation, and a ranked content-refresh queue. I also compared the learned model with a transparent baseline. Precision@50 became particularly useful because it connects the evaluation to the actual decision: if a team only has time to review the top 50 pages, how many of those pages are meaningful opportunities? This helped me understand that choosing an evaluation metric should start with the business or user decision, not simply with what metric is easiest to calculate.

Another important change happened when I developed V2. I did not want the natural-language component to replace the machine-learning pipeline. Instead, I placed an agent layer on top of the existing outputs. This allowed a user to ask questions such as which pages should be refreshed first or what the highest-priority opportunities are, while keeping the underlying ranking evidence available. This made the project feel less like an isolated ML experiment and more like a usable decision-support system.

One of the biggest lessons I learned was that building an ML project involves much more than writing Python code. I had to think about data quality, leakage, evaluation, reproducibility, documentation, outputs, limitations, and how another person would understand and use the result. Preparing the project for a real submission also taught me the importance of showing the actual system working rather than relying only on screenshots or slides.

There are also clear limitations. The system does not guarantee that changing a highly ranked page will improve its future Google performance. Search performance is affected by many factors that are not represented in the available data, and historical relationships do not necessarily predict future outcomes. The ranked queue should therefore be treated as a starting point for human investigation, not as an automated SEO decision-maker. Being able to state this limitation clearly is something I now consider part of doing responsible machine-learning work.

If I continued the project, my next major goal would be to close the loop between recommendations and outcomes. A V3 could track which recommended pages were actually refreshed and then measure their future search performance. This would allow the system to learn from the results of its own recommendations instead of stopping at prioritization. I would also like to add richer explanations, uncertainty indicators, and a lightweight dashboard.

The three most transferable things I learned are, first, **start with the decision you are trying to support and choose the evaluation around it**. Second, **build reproducible workflows rather than isolated experiments**, because a useful model needs to be understandable and repeatable. Third, **treat limitations and human judgment as part of the product**, not as an afterthought.

Looking back from the end of the internship, I would tell my Week 1 self that the most valuable outcome was not simply building a model. It was learning how to take a problem from raw data through analysis, evaluation, product thinking, documentation, and public proof — and turn it into something another person can actually inspect, understand, and use.
